# Windows and WSL troubleshooting

This guide covers Matter commissioning when Matterbridge runs in WSL 2 and the
Matter controller, such as Home Assistant, runs elsewhere on the LAN.

## Known-good network shape

- WSL uses mirrored networking.
- IPv6 is enabled on the active Windows adapter and in WSL.
- The controller and Windows host can exchange IPv6 and mDNS traffic.
- Matterbridge listens on UDP ports 5353 (mDNS) and 5540 (Matter).
- The Hyper-V firewall permits inbound UDP port 5540 to WSL.
- Wi-Fi client isolation and VLAN rules do not separate the controller from the
  Windows host.

## Check mirrored networking

In a normal Windows PowerShell, inspect `%UserProfile%\.wslconfig`:

```powershell
Get-Content "$HOME\.wslconfig"
```

The configuration should contain:

```ini
[wsl2]
networkingMode=Mirrored
```

After changing this file, restart WSL and then restart Matterbridge:

```powershell
wsl --shutdown
```

## Check Windows IPv6

In Windows PowerShell:

```powershell
Get-NetAdapterBinding -ComponentID ms_tcpip6 |
  Select-Object Name, Enabled

Get-NetConnectionProfile |
  Select-Object InterfaceAlias, NetworkCategory, IPv4Connectivity, IPv6Connectivity

Get-NetIPAddress -AddressFamily IPv6 |
  Where-Object InterfaceAlias -NotMatch "Loopback" |
  Select-Object InterfaceAlias, IPAddress, PrefixLength, AddressState
```

The active LAN adapter should have IPv6 enabled and at least a link-local
address beginning with `fe80::`. A routable or unique-local IPv6 address is also
expected on an IPv6-enabled LAN.

## Check WSL IPv6 and multicast

In WSL:

```bash
sysctl \
  net.ipv6.conf.all.disable_ipv6 \
  net.ipv6.conf.default.disable_ipv6

ip -brief address
ip -6 route
ip maddr show
```

Both `disable_ipv6` values should be `0`. The active interface should have an
IPv6 link-local address and an IPv6 route. Its multicast memberships should
include IPv4 mDNS `224.0.0.251` and IPv6 mDNS `ff02::fb`.

## Check Matterbridge listeners

Start Matterbridge, then run this in another WSL terminal:

```bash
ss -ulpn | grep -E ':(5353|5540)'
```

Matterbridge should own UDP listeners on ports 5353 and 5540 for IPv4 and IPv6.
If it does not, inspect the Matterbridge terminal for startup errors before
attempting commissioning.

## Permit Matter through the Hyper-V firewall

Mirrored WSL networking has a separate Hyper-V firewall. Windows normally
provides WSL with inbound mDNS rules for UDP port 5353, while the default inbound
Hyper-V policy remains blocked. Discovery can therefore succeed while the
Matter session on UDP port 5540 times out.

Inspect the policy in a normal PowerShell:

```powershell
Get-NetFirewallHyperVVMSetting -PolicyStore ActiveStore |
  Select-Object Name, Enabled, DefaultInboundAction, DefaultOutboundAction

Get-NetFirewallHyperVRule -PolicyStore ActiveStore |
  Where-Object DisplayName -Match "mDNS|Matterbridge" |
  Select-Object DisplayName, Direction, Action, Protocol, LocalPorts
```

Run this once in an **Administrator PowerShell** to add only the required Matter
port:

```powershell
New-NetFirewallHyperVRule `
  -Name "Matterbridge-UDP-5540" `
  -DisplayName "Matterbridge UDP 5540" `
  -Direction Inbound `
  -VMCreatorId "{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}" `
  -Protocol UDP `
  -LocalPorts 5540 `
  -Action Allow
```

The rule takes effect immediately. Keep the default inbound policy blocked;
opening all inbound WSL traffic is unnecessary.

Verify the rule:

```powershell
Get-NetFirewallHyperVRule -PolicyStore ActiveStore |
  Where-Object Name -EQ "Matterbridge-UDP-5540" |
  Select-Object DisplayName, Enabled, Direction, Action, Protocol, LocalPorts
```

To remove it later, use an Administrator PowerShell:

```powershell
Remove-NetFirewallHyperVRule -Name "Matterbridge-UDP-5540"
```

## Use the correct Home Assistant flow

For first commissioning, use the Home Assistant Companion app and select **Add
Matter device**, followed by the new-device or not-already-in-use option. Scan
Matterbridge's QR code or enter its initial setup code.

Do not use the already-in-use or sharing flow for first commissioning. That flow
requires a temporary multi-admin code generated by a controller that has
already commissioned the bridge.

Keep the phone on the same LAN, enable Bluetooth, and ensure the Home Assistant
Matter server can reach the Windows host over IPv6.

### Android succeeds but Home Assistant reports an error

On Android, the commissioning flow can first add Matterbridge to an Android
Local Fabric and then open a temporary multi-admin window for the Home Assistant
Matter server. These Matterbridge log entries show that the first stage
succeeded:

- `addNoc success`
- `commissioningComplete` with `errorCode: 0`
- `Server node for Matterbridge commissioned successfully`
- `openCommissioningWindow`

Home Assistant must then make a second PASE connection and add its own fabric.
If no second pairing request appears before the temporary window expires, the
failure is in the handoff from Android to the Home Assistant Matter server, not
in the initial Matterbridge commissioning.

Check all of the following before retrying:

1. In Home Assistant, open **Settings > System > Network** and set IPv6 on the
  active adapter to **Automatic** or **Static**, not disabled.
2. Prefer Home Assistant OS with the official Matter Server app. A custom Matter
  Server container must use host networking and meet its IPv6 and mDNS
  requirements.
3. On Android, set the Home Assistant Companion app's Location permission to
  **Allow all the time**. The Google Matter UI is in the foreground during the
  handoff, so **Only while using the app** can prevent the Companion app from
  reading the Wi-Fi network information it needs.
4. Keep Android, Home Assistant, and the Windows/WSL host on the same flat LAN
  without client isolation, VLAN filtering, or multicast optimization.

After this partial success, the original Matterbridge setup code is no longer
valid because one fabric exists. Remove Matterbridge from Android under
**Settings > Google > Devices & sharing > Matter devices** if it is listed. If
that does not remove the fabric, stop Matterbridge and reset commissioning:

```bash
"$HOME/.local/bin/matterbridge" --reset
"$HOME/.local/bin/matterbridge" --bridge
```

The reset removes Matterbridge commissioning fabrics but preserves the plugin
registration and PurpleAir configuration. Use the newly displayed QR code for
the next new-device attempt.

## Symptom guide

| Symptom | Likely cause | Check |
| --- | --- | --- |
| Matterbridge never appears | mDNS cannot cross the network boundary | UDP 5353 listeners, multicast membership, VLAN and Wi-Fi isolation |
| The code is accepted, then pairing times out | Matter traffic is blocked after discovery | Hyper-V inbound UDP 5540 rule |
| Home Assistant requests a sharing code | The already-in-use flow was selected | Use the new-device flow for first commissioning |
| Matterbridge reports success but Home Assistant reports an error | Android fabric succeeded but the HA Matter server handoff failed | HA IPv6, Matter Server networking, and Companion Location permission |
| Matterbridge reports `not commissioned` | No fabric has completed commissioning | Expected before the first successful pairing |
| Pairing fails after firewall changes | Stale WSL or Matterbridge process | Run `wsl --shutdown`, restart both services, and retry |

## Collect useful diagnostics

Capture these details when a failure remains:

```powershell
Get-NetConnectionProfile
Get-NetAdapterBinding -ComponentID ms_tcpip6
Get-NetFirewallHyperVVMSetting -PolicyStore ActiveStore
Get-NetFirewallHyperVRule -PolicyStore ActiveStore |
  Where-Object DisplayName -Match "mDNS|Matterbridge"
```

```bash
ip -brief address
ip -6 route
ip maddr show
ss -ulpn | grep -E ':(5353|5540)'
```

Also retain the Matterbridge lines written during the failed attempt. Do not
publish QR codes, manual setup codes, fabric credentials, or other commissioning
secrets in an issue or public log.
